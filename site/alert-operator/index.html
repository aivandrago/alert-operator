Alert Operator keeps a live inventory of your Prometheus alert rules and grades each one from Prometheus' own history: never loaded, can never fire, noisy, flapping, always silenced, nobody owns it. Read-only: it never touches a rule, a route or a silence.

The problem

Nobody knows which alerts would actually wake them up.

A cluster collects alert rules from kube-prometheus, from every Helm chart and from every team. After a year the rule set is a mix of rules that work, rules that cannot work and rules everyone has learned to ignore — and nothing tells you which is which.

Silently ignored

A PrometheusRule whose labels miss the Prometheus ruleSelector is accepted by kubectl apply and never loaded. The team thinks it is covered.

Can never fire

The app renamed its metric; the rule still queries the old name. A valid expression that selects nothing, forever.

Noise and no owner

Four rules produce most of the pages, one has been silenced for months, and a third of the rules have no team, no runbook and no severity.

Linters check rules before they ship. On-call tools see alerts after they fire. Nothing watches the rule set itself, in the cluster, all the time.

Findings

Ten questions asked of every rule, every fifteen minutes.

Each answer comes from something you already run: the Kubernetes API, Prometheus' rules API and its own ALERTS history, and Alertmanager's silences.

critical

NotLoaded

Defined in a PrometheusRule, absent from Prometheus — with the selector that excluded it.

critical

LoadError

Prometheus reports the group unhealthy or the last evaluation failed.

warning

DeadQuery

A selector in the expression matches no series, so the rule cannot fire. absent() is understood.

warning

Noisy

More activations in the window than the scope allows.

warning

Flapping

Fires often and resolves fast: many activations per day, short median duration.

warning

AlwaysSilenced

Firing, but covered by a silence most of the time. Fix it or delete it.

warning

Unowned

No team from the rule, its object or its namespace.

info

NeverFired · NoRunbook · NoSeverity

Quiet for the whole window; missing runbook_url; missing or unknown severity.

API · proposed

Declare the scope. Read the verdicts.

Group alerts.hypersurgery.dev, version v1alpha1 (proposed). You write one AlertScope; the operator writes one AlertRule per rule, in the rule's own namespace, and removes only what it wrote.

alertscope.yamlyou write
apiVersion: alerts.hypersurgery.dev/v1alpha1
kind: AlertScope
metadata:
  name: main
spec:
  prometheus:
    url: http://prometheus-operated.monitoring:9090
    resourceRef: { namespace: monitoring, name: k8s }
  alertmanager:
    url: http://alertmanager-operated.monitoring:9093
  ownership:
    teamFrom:
      - ruleLabel: team
      - namespaceLabel: hs/team
    requireRunbook: true
  quality:
    window: 30d                # capped to real retention
    noisy:    { firingsAbove: 50 }
    flapping: { activationsPerDayAbove: 10, medianDurationBelow: 10m }
  queryBudget:
    timeout: 20s
    maxQueriesPerMinute: 120
alertrule/paymentshighlatencythe operator writes
spec:
  source:
    kind: PrometheusRule
    name: payments-api
    alert: PaymentsHighLatency
  for: 5m
status:
  loaded: true
  team: payments
  quality:
    activations: 212
    medianFiringDuration: 4m
    firingFraction: 0.06
    lastFired: "2026-11-07T08:40:00Z"
  findings:
    - type: Noisy
      message: 212 activations in 30d (limit 50)
    - type: NoRunbook

Metrics carry the same verdicts — hs_alert_rule_findings, hs_alert_rule_activations, hs_alert_rules — so a Grafana panel or an ordinary Prometheus rule can track the clean-up.

Safety

It grades your alerts. It never touches them.

Read-only towards your monitoring

Get, list and watch on PrometheusRule and Prometheus; read-only calls to Prometheus and Alertmanager. No write path exists in v0.1.

Deletes only what it created

The only objects it writes are its own AlertRule mirrors, marked as such. Anything else is left alone, even with the same name.

Gentle on Prometheus

Timeouts, concurrency and a query rate limit are part of the API, and the operator reports when it hits them.

Never judges on missing data

The window is capped to the retention Prometheus actually has, and an unreachable Prometheus marks verdicts stale instead of erasing them.

Roadmap · proposed

Read first. Write later, opt-in, and only what it owns.
